1. Executive summary

FolderPilot organizes, finds and cleans files. You talk to an AI agent in plain language ("put all invoices from Alpha in a folder per year"), set rules, and FolderPilot detects duplicates and bad files, writes captions, and lets you search by meaning. Every change is shown first as a plan that a person approves; everything is logged and can be undone; and the AI can never delete anything.

It is aimed first at small offices — agencies, accountants, law firms — and later at consumers. It works in three ways (modes) with the same interface: on files where they already live (Connect: Google Drive, OneDrive, Dropbox), on FolderPilot's own storage (Cloud), or entirely inside the customer's own systems (Private).

2. What FolderPilot is

The problem

Small businesses drown in files: invoices named scan_0042.pdf, five copies of the same contract, holiday photos mixed with receipts, shared drives nobody dares to clean. Tidying them takes hours, and existing tools either only search, or "clean" by deleting things — which nobody trusts.

The answer

  • Understands files — reads names, dates, short text and small previews, and works out category (invoice, contract, photo…), client, date, amount and document type, plus a caption and a suggested name.
  • Proposes, never acts alone — every change is a plan you see before anything happens ("Move 37 files into Invoices/2025 · before → after").
  • Talk or set rules — ask the agent in plain language, or write rules ("IF category is Invoices THEN move to Invoices/{year}/{client}").
  • Finds clutter — exact duplicates, look-alike photos, blurry/dark/tiny images, screenshots; suggests which copy to keep.
  • Finds things — "the signed NDA with Alpha" works even if those words aren't in the file name.
  • Safe by design — audit log of everything, undo per action or batch, recoverable trash, and the AI has no delete capability at all.

Who it's for

B2B first: small offices, agencies, accountants, law firms — teams of 2–50 people with shared folders. Roles (owner, admin, editor, viewer) and approvals fit how they work. Consumers second: one person tidying their own Drive or photo folders.

3. Non-negotiable principles

These six rules from the product spec shape every feature and are enforced in code, not just in the UI.

PrincipleWhat it meansHow it is enforced
1. The AI can never deleteNo delete tool exists anywhere — not in the agent, not in the MCP server. The AI may only flag files "suggested for deletion". Only a person trashes files, and trash is recoverable (FolderPilot's trash or the provider's own trash; default retention 30 days).The engine rejects trash/restore in plans from agents, rules and MCP clients at creation, approval and execution. A type-level test proves the storage interface has no delete method.
2. Plan → Approve → ExecuteEvery change by agent, rule, MCP client or bulk action is first a plan (before/after, file count). Nothing changes until someone with permission approves. Admins may allow auto-run for small agent plans (off by default) and for rules explicitly set to "auto".The engine is the only code path that changes files; it checks the approver's role and the plan's status.
3. Everything audited and reversibleAppend-only audit log; undo per action, per batch, or "everything the agent did since…". Undo checks if a file changed meanwhile and asks instead of overwriting.A database trigger blocks UPDATE/DELETE on audit_events. Undo writes new events.
4. Privacy by modeThe AI only ever receives thumbnails (≤512 px) or extracted text, never whole files. In Private mode nothing leaves the customer's environment except to the AI endpoint they chose. Customer files are never used for training.Analysis code produces thumbnails/text excerpts before any AI call; logs never contain file contents.
5. Tenant isolationEvery query is limited to one organization. Tokens and keys are encrypted at rest.A single scoped data-access layer; AES-256-GCM with keys bound to their owner (space, org or server).
6. Simple, calm UI"Clean Ledger" theme, light and dark; familiar cloud-drive conventions with FolderPilot's own look.Shared design tokens and components (packages/ui).

5c. The action & plan engine

The heart of FolderPilot (packages/core): the only code that changes files.

Proposeagent, rule, person, MCP
→
Plansteps with before → after, file count
→
Approveperson with permission (or auto rule / small auto-run)
→
Executein batches, version-checked, resumable
→
Audit + Undoone event per step; inverse plan
  • Step types: move, rename, create folder, tag/untag, caption, set category, flag/unflag, trash (people only), restore (people only).
  • Statuses: plans are pending → approved → executing → executed / partially failed / cancelled; steps are pending / done / failed / conflicted / skipped. A plan can be edited before approval (untick steps).
  • Conflict checks: each file step remembers the file version it was planned against. If the file changed or disappeared, the step is marked conflicted and nothing is overwritten; you choose Skip or Apply to the current file. Moves never overwrite: a taken name becomes "name (2)".
  • Crash-safe: the index change, the audit event and the step status are written in one database transaction; re-running skips finished steps and recognizes a move that already happened.
  • Undo: one event, one batch, or "everything the agent did since …". Undo writes new audit events pointing at the ones it reverses; undo of an undo is refused; undo refuses to overwrite files changed since.
  • Trash bookkeeping: original path, who trashed it, kept until (30 days default).

5d. Local analysis — no AI cost

One analyzer (packages/analysis) runs in the browser (Web Workers) and on the server (worker service).

What it computes per file

  • SHA-256 hash (exact duplicates; partial hash for files over 256 MB)
  • dHash perceptual hash (near-duplicates: Hamming distance ≤ 6, configurable)
  • Blur score (contrast-normalized Laplacian), brightness
  • Width/height, tiny-image check, screenshot heuristic
  • EXIF (camera, date taken, location data)
  • Text excerpt: TXT/CSV/MD, DOCX (mammoth), PDF first pages (pdf.js), Google Docs/Sheets/Slides via export

What you see

  • Duplicates & Bad Files page: exact-copy groups, look-alike groups, blurry/dark/tiny/screenshots
  • "Keep best" suggestion per group (resolution, sharpness, name, date)
  • Review mode: one by one, ← trash / → keep, Esc to stop
  • "Trash the copies" button — a human action, recoverable
  • Verified on a 537-file messy sample: 70 copy groups, 6 burst-photo groups, 17 blurry, 10 dark, 15 tiny, 81 screenshots, in about 11 seconds

5e. The AI layer

One interface (packages/ai) with four jobs: describe an image (from a ≤512 px thumbnail), describe text, chat with tools (streaming), and make embeddings for search by meaning.

ProviderUse

  • FileInsight per file: category, tags, caption, suggested name, entities (client, date, amount, document type), confidence and a reason. Strict JSON validated by zod; output always English.
  • Needs Review: anything below the confidence threshold (default 0.6) is never guessed — it lands in Needs Review with Accept / Set category. A manual recategorization offers "Make this a rule?".
  • Prompt context: the organization's categories and active plain-language rules are included.
  • Cost controls: per-organization monthly AI budget (default 1,000 files) with a usage meter; results cached by content hash (same file = no second AI call); every call recorded in ai_usage.
  • Settings → AI for your organization (admins): pick provider, write-only keys ("saved — type to replace"), budget, Test connection. Keys are encrypted and bound to the organization.
  • AI status pill in the top bar: "FolderPilot AI", "Local AI", "Your cloud: …" or "AI off".

5f. Rules

  • Structured rules: IF conditions THEN actions. Conditions: file type, extension, name/content contains, regular expression (validated for safety), date range, size, folder, AI category, client, document type, has flag, source space. Actions: move to a path with variables {year} {month} {category} {client} {docType}, rename by pattern, tag, caption, flag for review, set category.
  • Plain-language rules: free text ("Anything from the tax office goes to Taxes") that's added to the AI's context; Convert to structured asks the AI to turn it into a rule, shown as a proposal you can edit.
  • Order: structured rules by priority → plain-language rules via the AI → AI default. First matching move wins; tags add up.
  • Mode per rule: Suggest (creates plans in Pending Approvals) or Auto (applies by itself — still audited as rule:<id> and undoable). Only admins can make a rule Auto; rules can never trash.
  • Scope (all spaces or one), schedule (on new/changed files only, hourly, daily, weekly), reorder, pause, archive (rules are never deleted — archiving is itself audited and undoable).
  • Test rule dry-run: affected count and the first 10 before → after changes; nothing changes.
  • Triggers: after files are analyzed (new/changed), "Run on folder", "Run all", and a 15-minute schedule tick on the server. On "This device" they run while the app is open.

5g. The agent

A streaming chat in the right-hand panel, in mini mode, and from the command palette (Ctrl/⌘+K → "Ask the agent: …"). Always answers in English.

ToolWhat it does
search_files, list_files, get_fileFind and inspect files (uses the hybrid search).
explain_categorizationWhy a file got its category (rule, AI reason, person).
propose_planMoves, renames, tags… returned as a Plan Card: summary, count, before/after, Approve / Edit / Cancel.

get_audit(filter), stats(question)Who changed what; counts and aggregates ("how many invoices from 2024?").
  • No delete, trash or approve tool — asking for one gets "there is no delete tool".
  • Text streams as it's written; each tool call shows as a line with a spinner, then a result ("Found 3 files"); Stop and New conversation buttons.
  • Scoped to what the person may access; viewers can propose but not approve.
  • Auto-run for small plans (spec §2): admins can let small agent plans run without approval (off by default). Rule changes, trash and restore always need a person.
  • Every tool call is logged (tool, short input summary — never file contents — success, duration) and visible in Audit Log → Agent activity.
  • Works without an AI too: on "This device" it falls back to keyword search.

5h. Search

  • Hybrid: Postgres full-text search (name, path, caption, tags, extracted text, client/document type — weighted, accent-insensitive, prefix matching while typing, plurals folded) plus pgvector similarity ("by meaning"), merged with reciprocal-rank fusion. Each result says whether it matched by words, by meaning or both.
  • Natural queries become chips: "invoices from Alpha 2025 pdf" → words + year 2025 + .pdf; kind words (photos, documents, spreadsheets), flag words (screenshots, duplicates, blurry), relative dates (today, last week, this year). Each chip can be removed with ×.
  • Filters with counts: type, modified date, category, space, flag, client.
  • Results show name, space, path, date, category, a highlighted snippet and a "by meaning" badge; open a preview (images, PDF, text, video, audio) with Download and "Show in its space".
  • Search by meaning needs an embedding model: the organization's AI if it can embed, else the server's Ollama, else words only (and the page says so). Vectors record which model made them; only same-model vectors are compared.
  • Measured: 40–125 ms per search on the 537-file sample.

5i. Google Drive (Connect mode)

  1. New → Connect a source → Google Drive (owners and admins). Google's consent screen asks for Drive access (OAuth with PKCE; a single-use, 10-minute state token tied to the person who started).
  2. Choose a folder: browse My Drive, "Use this folder" or "Use all of My Drive", name the space; the first scan starts.
  3. Scan and analyze: files appear and are analyzed. Google Docs/Sheets/Slides are read as their text/CSV export (shown as .gdoc .gsheet .gslides); thumbnails come from Drive.
  4. Organize: approved plans really move (addParents/removeParents), rename, and trash into Drive's own trash. Undo puts things back. An edit made in Drive since the plan was made is a conflict, never overwritten.
  5. Sync: the first scan is a full listing; afterwards FolderPilot reads Drive's change feed every 5 minutes (or on "Scan & analyze") and applies only what changed. Moved files keep their analysis; edited files are re-analyzed.
  6. Reconnect: if Google stops accepting the access (revoked, or the 7-day limit in Testing mode), the space shows a banner with Reconnect; the space and its analysis are kept.
  7. Space settings (⚙ in the header): rename, change folder (restarts that space's index), Disconnect — removes the space from FolderPilot and revokes access; never touches your Drive.
  8. Quick look on any file: preview, Download, Open in Google Drive.

Technical: plain HTTPS to Drive API v3 (no SDK); tokens refreshed automatically before expiry and on 401; backoff with jitter on rate limits and 5xx; shared drives supported; a file's version is its MD5 (or modified time for Google Docs), so moves/renames are never mistaken for edits; tokens stored AES-256-GCM-encrypted and bound to the space.

5j. Admin → Google Drive setup

A guided, one-time page (/admin/google, also linked from "Connect a source") for the server admin:

  • Six numbered steps, each with a button that opens the exact Google Cloud page (new project, Drive API, Google Auth Platform, Audience/test users, create OAuth client).

The storage adapter — how three modes share one engine

All file I/O goes through one interface. Nothing else touches files. Each source implements it:

interface StorageAdapter {
  list(path, cursor?)            → page of files          stat(ref)            → file + version
  readThumbnail(ref, maxPx)      → small image             readText(ref, max)   → text excerpt
  download(ref)                  → stream (preview only)   upload?(parent, file, name)
  move(ref, newParent, {expectVersion})                    rename(ref, newName, {expectVersion})
  createFolder(parent, name)     trash(ref)  ← people only  restore(ref)
  changes(cursor?)               → incremental sync        subscribe?(webhookUrl) → push updates
}                                // deliberately: no delete()

8. Security and privacy

In place today

  • Authentication: Better Auth sessions (14 days), HttpOnly cookies, Secure in production, passwords ≥ 10 characters.
  • CSRF: every state-changing request must come from the app's own origin (Origin/Referer check), plus CORS limited to the app.
  • Rate limiting: Redis-backed limits for auth (30/min), API (600/min) and search, with an in-memory fallback.
  • Input validation: zod at every API boundary.
  • Encryption at rest: provider tokens, AI keys and server settings with AES-256-GCM; each ciphertext is bound to its owner (space, organization or server key), so it can't be copied elsewhere.
  • Tenant isolation: scoped data layer; non-members get 404.
  • OAuth: PKCE, single-use state bound to the user, tokens never returned to the browser, revoked on disconnect.
  • Security headers: strict Content-Security-Policy (only own scripts plus a hashed inline theme script), no framing, nosniff, HSTS; file content always served as a download with nosniff (previews render from a blob, never from the API origin).
  • Path safety: server folders refuse path-traversal and symlink escapes; the web-app server never serves files outside its build folder.
  • Logs: structured, never contain file contents or secrets.
  • AI privacy: only ≤512 px thumbnails or text excerpts are sent; prompts never include whole files.
  • CI: dependency audit (high severity) on every push.

Still to do (spec §17)

  • GDPR: data export and account deletion with grace period (phase 11); DPA-ready documents in /docs.
  • Signed webhook verification for providers and Stripe (phases 8, 11).
  • Virus scanning (ClamAV) of uploads in Cloud mode (phase 7).
  • Formal security review checklist and penetration test (phase 14).
  • Email delivery (verification, invitations, password reset) — today links are written to the server log.

9. Hosting and deployment

How it runs

FolderPilot ships as one container (Dockerfile). On start, scripts/start.mjs applies database migrations, then runs the API (which also serves the web app from the same address) and the worker side by side; if one stops, both restart. FP_ROLE=server or worker splits them into separate services when you grow. Memory at idle: about 330 MB for both.

Option A — Render (one click, recommended to try it)

  • The render.yaml blueprint creates: the FolderPilot web service (Frankfurt/EU), PostgreSQL 16, and a Redis-compatible Key Value store (no-eviction). Secrets are generated automatically.
  • Start at render.com/deploy?repo=https://github.com/perdido101/folderpilot (or the "Deploy to Render" button in the README).
  • The public address (e.g. https://folderpilot-ab12.onrender.com) is picked up automatically.

14. What we haven't discussed yet

Topics not yet decided in our conversations. Several matter before real customers use FolderPilot.

Most important: Google's "restricted scope" verification. FolderPilot uses the full drive permission so it can organize existing files. Google classifies this as a restricted scope. In Testing mode it works for up to 100 named test users with re-login every 7 days. To open it to the public, Google requires app verification and a yearly independent security assessment (CASA), which takes weeks and has a cost. Alternatives: stay in Testing for pilots, use Google Workspace "internal" apps per customer, or a narrower scope (drive.file) that only reaches files the user picks — which limits what FolderPilot can organize. Microsoft and Dropbox have their own (lighter) review processes.

Business and product

  • Pricing — actual prices, free-tier limits, AI cost per file (and margin), storage price per GB, overage.
  • Brand and domain — a domain (e.g. folderpilot.app), logo, website/landing page, email sender address.
  • Legal — terms of service, privacy policy, data processing agreement (DPA) for B2B, sub-processor list (Render, AI provider, Google), cookie notice. Required for Google verification too.
  • Company setup — the legal entity that signs with customers and holds the Google/Microsoft/Stripe accounts.
  • Target market and languages — UI is English only by your choice; first market(s) and whether other languages come later.
  • Onboarding — starter rule packs per profession (accountants, lawyers, agencies), sample data, first-run tour.
  • Support — help center, contact, in-app feedback.

Operations

  • Production hosting — Render is ideal to try it; for customers decide region (EU), paid plans, separate staging and production, and possibly Hetzner/Fly for cost.
  • Backups and recovery — automatic Postgres backups, point-in-time restore, tested restore procedure; what happens if the encryption key is lost (stored tokens become unreadable — keep it in a password manager).
  • Monitoring — uptime checks, error tracking (e.g. Sentry), log retention, alerts on failed jobs and AI budget.
  • Email delivery — a provider (Postmark, Resend, SES) for verification, invitations, password reset, weekly summaries.
  • Scaling — splitting server/worker, worker concurrency, AI rate limits, very large Drives (100k+ files), queue monitoring.
  • Release process — versioning, changelog, database migration policy, feature flags.

Product questions

  • Trash retention and purge — today nothing is ever purged automatically; when and how permanent deletion happens (a human-only, admin-configured setting).
  • AI cost policy — which model per task, how many files per month per plan, what happens at the budget limit, re-analysis rules.
  • Data retention — how long the index, audit log and AI results are kept after disconnecting or cancelling.
  • Sharing and collaboration — comments, mentions, notifications, multiple approvers for big plans.
  • Mobile — a phone experience (the web app is desktop-first today).
  • Accessibility — formal WCAG review.
  • Analytics — privacy-friendly product analytics to learn what customers use.
  • Reporting — audit export (CSV/PDF) is planned; dashboards ("this month FolderPilot organized 1,240 files") are not.

15. Known limitations (today)

  • Email isn't sent — verification, invitation and password-reset links appear in the server log.
  • Google Testing mode — only listed test users; re-connect every 7 days (one click, analysis kept).
  • Drive sync every 5 minutes (or on demand) — instant push needs webhooks (with a public address; coming).
  • Render free plan — sleeps after 15 minutes; free database expires after 30 days.
  • Search by meaning needs an AI that can make embeddings (OpenAI-compatible, Ollama, or the server's Ollama); otherwise words only. Real embedding quality has only been tested with mocks.
  • Full-text search is language-neutral with English plural folding; other word forms rely on prefixes and meaning.
  • Files over 256 MB are indexed and hashed but not decoded or read for text.
  • Browser mode needs Chrome or Edge (File System Access API); browsers can't watch folders, so outside changes appear on Rescan; scheduled rules run only while the app is open.
  • Server-folder space (dev sample) is read-only until phase 9.
  • Agent and AI quality are tested with scripted mock AIs; real-model behavior needs your testing with a real key.
  • Trash is never purged automatically (by design until retention settings exist).
